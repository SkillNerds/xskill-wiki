What is KV Cache

Understand the mechanism that makes repeated API calls cheaper and faster — and why it matters for Agent workflows.

The Problem: Redundant Computation

Every time you send a request to a language model, the server must compute attention across ALL tokens in your input. For a 10-turn conversation, that means re-processing everything from the system prompt through all previous messages — even though most of that hasn't changed since last time.

This is like re-downloading an entire website every time you click a link, even though 95% of the page is identical.

The Solution: KV Cache

KV Cache (Key-Value Cache) stores the intermediate attention computation results on GPU memory. When your next request arrives, the server checks: "Does the beginning of this new request match something I've already computed?"

If yes — those tokens are served from cache. No re-computation needed.

Analogy: Think of it like a browser cache for web pages. If the HTML didn't change, the browser doesn't re-download it — it serves from the local cache. KV Cache does the same thing for GPU attention computation.

Longest Common Prefix Matching

The cache uses a "longest common prefix" strategy. It compares the token sequence of your new request against cached sequences, starting from the very first token. The match must be contiguous from the beginning — a matching suffix or middle section doesn't count.

# Request at Turn 1: [S₀ | U₀] → all computed fresh # Request at Turn 2: [S₀ | U₀ | C₁ | U₁] ↑ cached ↑ ↑ new ↑ # Request at Turn 3: [S₀ | U₀ | C₁ | U₁ | C₂ | U₂] ↑────── cached ──────↑ ↑new↑

The longer the shared prefix, the more computation is reused.

64-Token Block Alignment

In practice, KV Cache operates in chunks (commonly 64 tokens). The cache hit is aligned to block boundaries — if your prefix is 100 tokens long, 96 tokens (1.5 blocks) are cached, and the remaining 4 tokens plus new content are computed fresh.

This means very short prefixes (under 64 tokens) may not benefit much from caching.

Why This Matters: Cost and Speed

Cached tokens bring two advantages:

  1. Lower cost — API providers charge significantly less for cached input tokens (often 1/10th to 1/30th the price of uncached tokens).
  2. Lower latency — No computation means faster time-to-first-token. The prefix section is essentially "free" from a compute standpoint.
The flip side: If you modify the beginning of your message list (e.g., change the system prompt, insert a new instruction before old messages), the entire prefix changes and cache is invalidated. This is why message ordering and immutability matter for cost optimization.

What Breaks the Cache

  • Changing any token in the prefix (even one character in the system prompt)
  • Reordering messages
  • Context compression (summarizing old messages breaks the token sequence)
  • Switching to a different model endpoint
  • Cache eviction due to GPU memory pressure (high traffic periods)

Agent Mode vs Direct Chat: Cache Implications

Now here's the connection to the previous tutorial:

  • In Agent mode, messages are strictly append-only: S₀ + U₀ + R₁ + C₁ + T₁ + TR₁ + U₁ + R₂ + C₂ + ... — the prefix never changes, so cache hit rate approaches 100% over many turns.
  • In Direct Chat, the server strips reasoning (R), so the sequence seen by the cache is: S₀ + U₀ + C₁ + U₁ + C₂ + U₂ + ... — still append-only, but with a gap. When the client sends the full message (including R which the server discards), the token sequence may differ from what's cached, causing partial misses.

We'll quantify this difference precisely in the next tutorial.

Summary

  • KV Cache stores attention computations on GPU memory to avoid redundant work.
  • It uses longest-common-prefix matching — only the beginning of your request can be cached.
  • Cache operates in 64-token blocks.
  • Cached tokens are cheaper (1/10–1/30 price) and faster (no recomputation).
  • Agent mode's append-only structure is naturally cache-friendly; Direct Chat less so.

什么是 KV Cache

理解让重复 API 调用更便宜、更快的机制——以及它为什么对 Agent 工作流至关重要。

问题：冗余计算

每次你向语言模型发送请求，服务端都必须对输入中的所有 token 做注意力计算。一个 10 轮对话意味着：从系统提示词到所有历史消息，全部重新处理一遍——尽管其中大部分从上次以来根本没变。

这就像每次点一个链接都重新下载整个网站，尽管 95% 的内容和上次一模一样。

解决方案：KV Cache

KV Cache（Key-Value 缓存）在 GPU 显存中保存中间的注意力计算结果。当下一个请求到来时，服务端会检查："新请求的开头是否和我已经算过的东西匹配？"

如果匹配——那些 token 直接从缓存中读取，不需要重新计算。

类比：把它想成浏览器缓存。如果 HTML 没变，浏览器不会重新下载——直接从本地缓存提供。KV Cache 对 GPU 注意力计算做的是同样的事。

最长公共前缀匹配

缓存使用"最长公共前缀"策略。它从第一个 token 开始，逐个比较新请求的 token 序列与缓存中的序列。匹配必须从开头连续——中间或末尾的匹配不算。

# 第 1 轮的请求： [S₀ | U₀] → 全部重新计算 # 第 2 轮的请求： [S₀ | U₀ | C₁ | U₁] ↑ 缓存命中 ↑ ↑ 新的 ↑ # 第 3 轮的请求： [S₀ | U₀ | C₁ | U₁ | C₂ | U₂] ↑────── 缓存命中 ──────↑ ↑新↑

共享前缀越长，复用的计算越多。

64-Token 块对齐

实际上，KV Cache 按块操作（通常是 64 个 token 一块）。缓存命中会对齐到块边界——如果你的前缀有 100 个 token，那么 96 个 token（1.5 个块）被缓存命中，剩下的 4 个 token 加上新内容需要重新计算。

这意味着非常短的前缀（少于 64 token）可能从缓存中获益不大。

为什么重要：成本与速度

缓存命中的 token 带来两个好处：

  1. 更低的费用——API 提供商对缓存命中的输入 token 收费显著更低（通常是未命中价格的 1/10 到 1/30）。
  2. 更低的延迟——不需要计算意味着更快的首 token 返回时间。前缀部分在计算角度基本上是"免费的"。
反面：如果你修改了消息列表的开头（比如改了系统提示词、在旧消息前面插入新指令），整个前缀都会变化，缓存全部失效。这就是为什么消息顺序和不可变性对成本优化很重要。

什么会打破缓存

  • 修改前缀中的任何 token（系统提示词哪怕改一个字）
  • 重排消息顺序
  • 上下文压缩（对旧消息做摘要会打断 token 序列）
  • 切换到不同的模型端点
  • GPU 显存压力导致缓存被驱逐（高流量时段）

Agent 模式 vs 直聊模式：缓存影响

这里就联系到了上一篇教程的内容：

  • 在 Agent 模式中，消息是严格追加的：S₀ + U₀ + R₁ + C₁ + T₁ + TR₁ + U₁ + R₂ + C₂ + ... ——前缀永远不变，所以缓存命中率随着轮次增加趋近 100%。
  • 在直聊模式中，服务端剥离推理（R），所以缓存看到的序列是：S₀ + U₀ + C₁ + U₁ + C₂ + U₂ + ... ——仍然是追加的，但中间有间隔。当客户端发送完整消息（包含被服务端丢弃的 R）时，token 序列可能和缓存的不一致，导致部分未命中。

小结

  • KV Cache 在 GPU 显存中存储注意力计算结果，避免重复工作。
  • 使用最长公共前缀匹配——只有请求开头部分能被缓存。
  • 缓存以 64-token 块为单位操作。
  • 命中缓存的 token 更便宜（1/10–1/30 的价格）且更快（无需重新计算）。
  • Agent 模式的纯追加结构天然对缓存友好；直聊模式则较弱。
